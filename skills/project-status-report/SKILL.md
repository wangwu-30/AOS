# 项目状态汇报（Project Status Report）

## 概览

使用固定四段结构输出项目状态汇报：当前状态（Current State）、目标状态（Target State）、差距分析（Gap Analysis）、下一步计划（Next-Step Plan）。

优先把已有事实压缩成清晰判断；如果信息不足，明确写出假设、缺口和待确认项，不要用空泛措辞填充。

## 工作流

### 1. 确定汇报上下文

- 识别受众、时间范围、项目范围、输出长度。
- 如果用户没有说明，默认按“内部周报、面向直接协作者、长度 4 段到 8 段”处理。
- 如果有多个项目或里程碑，先拆分范围，再决定是合并汇报还是逐项汇报。

### 2. 抽取事实并做状态判断

- 仅使用当前上下文中可验证的进展、风险、阻塞、交付物、日期和负责人。
- 先区分事实与判断，再写汇报。
- 当前状态必须回答“现在到了哪里”；避免只写“推进中”“优化中”这类空话。

### 3. 计算目标与现状之间的差距

- 目标状态要描述项目希望达到的明确结果、里程碑或验收线。
- 差距分析要说明还缺什么、为什么还没到、主要阻断是什么。
- 能量化时优先量化，例如完成比例、剩余事项数、剩余风险项、预计日期偏差。

### 4. 形成下一步计划

- 下一步计划必须是可执行动作，不要写成抽象愿景。
- 优先包含动作、负责人、时间点、预期结果；缺失时至少给出动作和预期结果。
- 如果项目受阻，下一步计划要包含解阻动作，而不是继续重复当前工作。

## 输出规则

### 基础结构

默认按以下顺序输出：

```md
当前状态
- 已完成的关键事实
- 当前风险/阻塞
- 进度判断

目标状态
- 本阶段目标
- 验收条件或里程碑

差距
- 尚未完成的关键项
- 造成差距的原因
- 需要额外关注的风险

下一步计划
- 动作
- 负责人/协同方
- 时间点
- 预期结果
```

### 表达约束

- 先结论后细节，优先让读者快速理解状态是否健康。
- 缺少证据时，写“待确认”或“基于当前信息判断”，不要伪造确定性。
- 如果受众是管理者，压缩执行细节，突出风险、偏差、决策需求。
- 如果受众是执行团队，补足依赖项、责任人和近期计划。

## 缺失信息处理

- 不知道目标状态时，先从用户原始目标、里程碑、承诺日期中反推。
- 不知道当前状态时，只总结已知事实，并把未知部分放入差距或待确认项。
- 不知道下一步负责人时，可以先写动作与依赖，再标记“负责人待确认”。

## 质量检查

- 检查四段结构是否完整。
- 检查每一段是否回答了不同问题，避免“当前状态”和“差距”重复。
- 检查下一步计划是否可执行、可追踪。
- 检查语气是否与受众匹配。
